# Feature: Admin

**Status:** accepted
**Spec reviewed:** 2026-09-07
**Implementation verified:** not yet
**Owner modules:** `src/modules/users`, `src/modules/settings`, admin pages under `src/app/(app)/admin`

## Purpose

Everything an administrator needs to run the installation from the browser: setup, users, settings, AI, learnings, backups, jobs, audit log, export. No CLI is required for any admin task; the operator only edits environment variables and restarts for secrets.

## Setup and recovery

- ADMIN-B01 First boot prints `SETUP_TOKEN` (random, 32 bytes) to the log; `/setup` requires it, creates the admin, the principal person (linked to the admin unless "the principal is someone else" is chosen), workspace name, default locale, timezone; runs in one transaction locking `workspace` (the request's own, so a setup that fails to commit leaves nothing behind); a second submission after completion → 409. The exception is a retry after a lost response: for 15 minutes after completion, and until the next restart, the identical submission (same setup token, same fields, the new administrator's password) signs in as that administrator and returns the same user instead of failing. Concurrent identical submissions therefore both succeed with one administrator; any other submission after completion is still 409.
- ADMIN-B02 `/recovery` exists only when `RECOVERY_TOKEN` is set; accepts the token once, lets the operator set a new password for a chosen admin, then records the token hash as used (a restart with the same token is refused).

## Users

- ADMIN-B03 List, invite (create with a temporary password shown once), edit name and role, deactivate/reactivate, reset password (temporary, shown once), view sessions and revoke. Creating a user runs in the users service, which generates and hashes the temporary password and writes a `create` audit record naming the user's name, email and role, never a password or hash. An address another account already holds (in any case) is refused as a field error on `email` (`email_taken`) and writes nothing. Deactivation and password reset revoke all sessions of that user.
- ADMIN-B04 Last-admin protection: demoting or deactivating the last active admin → 422 `ADMIN-B04`.
- ADMIN-B05 Each member manages their own profile: name, password, locale, timezone, theme, numerals; changing password revokes other sessions.
- ADMIN-B06 Linking a user to a person (`people.user_id`) is done from the user page; one-to-one.

## Settings

- ADMIN-B07 Settings render from the registry as plain-language rows, each with the control its value calls for: text, a person, a language or numerals switch, a searchable time-zone list, a number with its unit, a percentage of target, a task view. The Workspace settings page holds the workspace itself (name, principal, language, time zone, numerals), the wallpaper and data retention; settings that belong to one part of the product sit on that part's admin page: when a KPI counts as on target on Objectives, the view the Tasks page opens on on Tasks, the AI on AI connection, note vocabularies on Notes. Every change saves at once and confirms with a toast, and a change to numerals, language, time zone or wallpaper re-renders the page at once; a reset control appears on a row whose value differs from its default. Workspace keys are admin-only; user keys appear in the profile. Values are validated on save; an invalid value shows the error above the sections.
- ADMIN-B08 Notes types editor (`notes.types`, `notes.default_type`) on `/admin/notes`: add, rename label per locale, disable (existing notes keep the identifier), choose the default (`NOTES-B20`).
- ADMIN-B30 Note templates editor (`notes.templates`) on `/admin/notes`: edit each template's label and body per locale, disable, add a template by identifier; an empty setting shows the built-in templates as the starting point (`NOTES-B27`).
- ADMIN-B09 KPI thresholds editor with validation and a preview of how many KPIs change status.
- ADMIN-B48 **Retention 0 means never** (ADR 0035). The three data-retention settings accept 0 to 3650 days (`retention.trash_days`, `retention.meeting_files_days`) and 0 to 100 copies (`retention.backup_count`), and 0 on any of them means never: the trash purge deletes nothing, the file archive job archives nothing, and no backup is pruned. The rows are named for what they do ("Delete trash permanently after", "Archive meeting files after", "Number of backups to keep"); each carries one line of help under its field, linked to the field through `aria-describedby`, saying in its own terms that 0 means never and nothing is deleted (meeting files are never deleted in any case, ADR 0034), with the 0 in the user's numerals; and while the field holds 0 the unit beside it is replaced by the state in words ("Never deleted", "Never archived"). An empty field is not 0: it is put back like any other invalid entry.
- ADMIN-B49 **Server timing.** Every API response carries `Server-Timing` with the session check (`auth`), the transaction that ran the handler (`db`) and the whole request (`total`), in milliseconds, on success and on error alike, so a slow response can be placed at the edge or at the origin from the browser. Pages do not carry it: an App Router layout cannot set response headers.

## AI

- ADMIN-B10 AI page: connection status and Test connection; model selection from the allowlist with feature matrix; capability toggles; monthly budget with usage bar; fallback toggle; disclosure list of data sent per capability; usage table (30 days by capability: calls, tokens, cache rate, estimated cost, pricing version).
- ADMIN-B11 Learnings: active version with content; proposals list with diff, source feedback, Activate, Reject, Edit-and-activate, Reset; history of versions.

- ADMIN-B23 OpenRouter is the only AI provider. Saved credentials take precedence over `OPENROUTER_API_KEY`; absent both, AI is disabled. Direct Anthropic configuration and provider selection are unavailable. Connection checks use bearer authentication against `/api/v1/key`, a ten-second timeout, and no retries; they reject malformed responses and exhausted key limits and map invalid credentials, billing, rate limits, network failures and other provider failures to safe categories. AI model settings accept namespaced OpenRouter IDs (including variants and `~` aliases), rejecting unqualified IDs, URLs and malformed IDs. Syntax does not imply capability compatibility. Both locales disclose forwarding to downstream model providers.

- ADMIN-B24 Administrators can save, replace, and remove an OpenRouter API key on `/admin/ai` without restarting. The selected saved credential overrides environment configuration; removal restores environment fallback. A password field is never prefilled, and successful save clears the submitted key and announces confirmation. A prominent persistent “Key saved securely” indicator survives reload; a saved key changes the form action to “Replace key”. Connection status is separate: untested credentials show “Connection not tested yet”, and failed tests explicitly show failure. API reads expose only provider and credential source; members cannot read or mutate credentials. Keys are stored separately from the settings registry with AES-256-GCM authenticated encryption using a domain-separated key derived from `SESSION_SECRET`; changing that secret requires re-entering the API key. Audit entries contain only operation and provider, never plaintext or encrypted keys. General exports exclude credentials; database backups retain encrypted credentials and require the original `SESSION_SECRET` to decrypt them. Invalid or unreadable stored credentials fail closed.

- ADMIN-B26 Task and note generation uses durable, revision-snapshotted jobs with required structured outputs, no tools or model fallback, and at most two provider attempts. Admission enforces enabled capability switches, model limits, a workspace monthly spending limit in US dollars (ADR 0033: each request reserves the most its two attempts can cost at the selected model's catalog prices; spent plus reserved cost may not pass the limit) and per-user hourly limits (30 breakdown/refinement, 60 tags). Administrators can change switches and the limit and view current-month spend, usage and reservations plus thirty-day per-capability token/cost estimates. Generation HTTP 404 failures are terminal model-routing failures and explain model selection/provider preferences without claiming invalid credentials. Generation HTTP 402 failures are terminal billing failures and display a localized insufficient-credit/spending-limit message. Unknown failed-call usage retains conservative estimated consumption. See ADR 0017; current development awaits verification.

- ADMIN-B29 `GET /ai/availability` answers three things, not one: the capabilities this reader can use, whether the workspace is `configured` for AI at all (a credential exists and at least one capability is switched on), and whether this reader `canConfigure` it (an administrator). A record shows the absence accordingly, in the slot and weight of the control it stands in for rather than above the record's own title. A workspace that has never set AI up is not faulty: only a reader who can turn it on is told, and they are invited to rather than asked to re-check a setting nobody changed. A workspace that does use AI and cannot reach it is told to everyone, with a re-check, because a member has lost a control they had and the answer can change. Either way one info control discloses what AI would do on that record, and the route to switch it on appears only for a reader whose role can, so nobody is sent to a page that refuses them. Role stays out of Account's schemas (ACCT-I02); this is AI answering for itself.
- ADMIN-B25 The AI page loads the OpenRouter catalog and offers default (task breakdown and note refinement) and fast (tag suggestions) model selections. Only text models advertising structured outputs appear. Catalog requests omit the SDK’s `anthropic-version` header so OpenRouter returns native model IDs, pricing and supported parameters rather than its paginated Anthropic compatibility catalog. Saving rejects models absent from this compatible catalog. Admission rechecks model support and token limits; stored IDs alone never enable a capability.

## Backups and export

- ADMIN-B12 Backups page: schedule (from `schedules`), retention (`retention.backup_count`, default 14: after each backup is written, the newest that many verified backups are kept and older ones deleted; a folder that does not verify as a backup is never counted or deleted; 0 keeps every backup, ADMIN-B48), list of backups with size, manifest status (the list, which the page polls, checks each manifest and the file sizes it names; the checksums are read by Download and restore), Create now (enqueues `system.backup`), Download (admin, streamed), Delete (admin, `DELETE /admin/backups/:id`: confirmed first, removes that backup's folder for good, refuses with 404 a folder whose manifest does not name it, and is written to the audit log), Verify (checks manifest checksums).
- ADMIN-B13 Restore is a command (`pnpm backup:restore <file>`) documented on the page; it verifies the backup, puts the app in maintenance mode, restores DB and files (ADMIN-B31), and exits maintenance. Maintenance mode returns 503 for all routes except health. One backup or restore runs at a time, across the server and the restore command: both hold a lock file in `BACKUP_DIR` naming their process, which a later one takes over only when that process has gone; a second is refused. While maintenance mode is on, the job runner starts nothing.
- ADMIN-B31 **Restore is failure-atomic for files.** `files.tar` is extracted into a unique staging directory inside `FILES_DIR` (never into live files), the database file from the backup is checked with `PRAGMA integrity_check` and swapped over the live one (client closed, written beside, renamed over, `-wal` and `-shm` removed, client reopened), and only after that swap are the live entries retired and the staged entries moved into place; a failed move puts both sets back, and if even that fails the retired entries stay in a `.previous-*` directory rather than being deleted. The staging directory is always removed. Maintenance mode is cleared whether the restore succeeds or fails, with two exceptions, so the app never serves a database and files from different backups: if the database file has been swapped but the staged files cannot be moved into place; and if the marker was already on when the restore started, because an earlier restore did not finish. In both cases the app stays in maintenance mode until a restore succeeds, and the command tells the operator to run the same restore again. Clearing tolerates a file that is already gone. A stale staging directory left by an interrupted restore is removed at the start of the next one. Only one restore runs at a time: the command holds the in-process restore lock (`core/db/locks.ts`) for the whole restore, and a second restore started meanwhile is refused before it touches staging or maintenance mode. Backups never capture restore staging or retired directories (ADR 0024, ADR 0026, ADR 0029).
- ADMIN-B32 **Restore refuses untrustworthy archives.** Before activation each file's size is compared with the manifest's `bytes` and then its checksum. Extraction streams through counters and stops at the first entry past a limit, before writing it: at most 200 000 entries, and expanded bytes no larger than both `FILES_QUOTA_GB` and the archive's own verified size. Only regular files and directories are accepted; symbolic links, hard links, device entries, `..` paths, absolute paths and truncated entries fail the restore instead of being skipped.
- ADMIN-B33 **Backups, restores and jobs stop cleanly.** Every phase of a backup (database snapshot by `VACUUM INTO`, archive, checksums, manifest, verification) observes the job's abort signal, and a backup that does not finish removes its staging directory. A restore observes `SIGINT`/`SIGTERM` and a one-hour deadline in every phase before the file swap; the swap itself is never abandoned half way because the database has already committed. On `SIGTERM` or `SIGINT` the job runner stops claiming, lets running handlers finish for up to `JOBS_DRAIN_SECONDS`, then aborts the remainder and gives them five seconds to record the attempt, which is retried later whatever the job kind: an interrupted AI job is not recorded as a provider failure. A job cancelled by a user keeps its cancelled outcome. The production image sets `NEXT_MANUAL_SIG_HANDLE` so the process exits after this drain (143 for `SIGTERM`, 130 for `SIGINT`) instead of when Next's HTTP server closes.
- ADMIN-B14 Export `POST /admin/export` enqueues `system.export` producing a zip: `manifest.json`, one JSON file per table (excluding sessions, login_attempts, idempotency_keys, private notes of other users), markdown renders of notes and briefs, original documents that are available. The requesting admin's own private notes are included under their user id. Download when ready.

## Service guarantees

- ADMIN-B36 **Every save is all or nothing.** Each public service method that writes owns its transaction: called directly (a script, another module, a test) it opens one; inside the request handler's transaction it runs as a savepoint. A failure at any step undoes every write that method made. This covers the AI services too: starting, applying, discarding and restoring a task breakdown or a note proposal each commit as one unit, and a callback that writes on the method's behalf (the tasks a note proposal creates) receives the method's own context, so its writes roll back with the rest. A test discovers every module's `service.ts` and every file under its `ai/` except the route handlers, and fails if any writing export loses this. Savepoint statements are transaction control and do not count against the per-request query budget.
- ADMIN-B37 **A full job queue is a retryable refusal.** When a job kind already has 100 queued or running jobs, enqueueing answers 429 `rate_limited` with `{ scope: "queue", kind, retryAfterSeconds: 30 }` and a `Retry-After` header, never 500. Routes that enqueue declare it, and OpenAPI lists the 429 for them.
- ADMIN-B38 **A database error is not a crash.** A failure the database reports outside any request's own statement — the file closed and reopened by a restore, a connection the client drops, a write-queue wait that runs out — is logged as a warning (the error serialized per ADMIN-B18) and the application keeps serving: the client discards that connection and opens a new one on the next query. It never surfaces as an uncaught exception. Queries in flight at that moment fail through their own request, as any database error does.

## Shell placement

- ADMIN-B19 The administration entry is in the account menu behind the avatar in the header, directly under Account, not in the sidebar among the everyday modules: it is an occasional destination for one role. It stays absent for members (ADMIN-B03) and keeps its place in the mobile bar. The account menu's lines, the name and the email included, start at the reading edge: right in Arabic, left in English.

- ADMIN-B39 **Overview.** `/admin` is an overview, not a page of its own subject. It reads only the lists the administration pages already load (members, AI connection, backups, jobs of the last seven days, audit) and states first whether anything needs the administrator: jobs that failed in the last seven days, no backup ever taken, and a failed AI connection test, each with a link to the page that resolves it. Nothing is raised until those lists have arrived, and a workspace that never set AI up is not raised (ADMIN-B29); with nothing to raise it says so in one line. No threshold is invented: the age of the last backup and of the last audited change is shown, not judged. Below that it lists every administration page in its group with one line of its current state (active members and administrators, connection state, last backup, job failures or activity, last change; a fixed description for pages without a state). It polls at the list cadence (60 seconds), not the two-second cadence of a page watching its own jobs.
- ADMIN-B40 **Grouped administration navigation.** One definition (`src/ui/layout/admin-sections.ts`) groups the pages as Workspace (workspace settings, AI connection, members), Work and strategy (tasks, notes, objectives and KPIs) and Maintenance (backups, jobs, audit log). From `lg` it renders as the same glass views rail a list page uses, in the same place and size — the overview first, then each group under its heading — marking the page shown with `aria-current`, the selected wash and the accent icon. Below `lg` there is no list: the overview's index is the same list, and every administration page carries one link back to it above its title. The page title is the only heading naming the page; the overview's is "Administration".
- ADMIN-B41 **Restore notice.** The backups page shows a "Restore a backup" panel with a "Coming soon" chip and one sentence that restoring from the page is coming soon and that downloaded backups can already be kept safely. It shows no server command; restore remains the command in ADMIN-B13.
- ADMIN-B42 **Wallpaper.** Administrators choose the night theme's wallpaper for the whole workspace from Settings, as the `workspace.wallpaper` setting: Ribbon, Copper, Jade, Neon, Folds, Stone, Arc or Sky, photographs served from `public/wallpapers/`, or an image of their own (ADMIN-B47). The choice is a radio group of swatches, each a picture of the wallpaper with its name; choosing saves at once and repaints the window behind the page. Every page reads the setting while it renders and carries it on `<html>` as `data-wallpaper`, with its tone as `data-wallpaper-tone`; a database that cannot be read, a saved value that is no longer a wallpaper (the retired Indigo, Fan and Mist) or an uploaded image that is gone falls back to the default, Jade. The interface's accent follows the wallpaper (ADR 0037): each built-in carries the accent computed from its photograph, and a wallpaper with no usable colour keeps the sage of ADR 0036.
- ADMIN-B43 **Readable history and maintenance.** The audit log groups changes by day (Today, Yesterday, then the date) and shows each as a sentence of action and kind (Edited note), the record it names when the change carries a title, name or setting (a setting by its settings-page name), who made it (System when no member did) and how long ago, with the exact time on hover; the changed values fold away under Details as a left-to-right field list. Background jobs and backups show their kind in words and their state as a chip in words (Queued, Running, Done, Failed, Cancelled). An action or kind the catalog does not know is shown by its own name with the punctuation removed.
- ADMIN-B44 **Backup download.** Each backup on the Backups page offers Download with its size; `GET /admin/backups/:id/download` (admin only) verifies the backup as a restore would and streams its folder (manifest, database, files) as one `.tar` named by date, and the download is written to the audit log. A backup that no longer verifies is not offered (404).
- ADMIN-B45 **AI page.** Three short sections: Connection (whether it works, with a test, and the key, saved keys never shown, replaced in place), Features (one on/off switch per feature named by what it does, saved at once, and the monthly limit in US dollars, typed to the cent, blank for no limit and saved when the field is left) and This month (dollars spent and tokens used, a warning at 80% of the limit counting what active requests may still cost, and requests and cost per feature). Connection failures are explained in words by cause (credit, key, network, rate limit, provider). The model choice and the note on what is sent to the provider are folded under Advanced.
- ADMIN-B46 **Backups in progress, told truthfully.** A running job whose lease has expired has no live runner behind it (a crash, a restart, a database copied while it ran), so it never holds its dedup key: enqueueing with that key recovers it as a claim would (the attempt is recorded as abandoned with `lease_expired`; the job is queued again while attempts remain, otherwise failed, freeing the key for a new job), and the claim sweep fails a running job whose lease expired on its last attempt. `GET /admin/backups` returns `meta.runner` (whether this server runs background jobs, `JOBS_ENABLED`) and `meta.job` (the latest backup job). After Create backup the page says the backup started, shows a queued or running backup as its job row with its state and disables Create while it is active, keeps polling, and says when it finished or failed; when background jobs are off it says that no backup will be made until they are turned on and the app restarted, instead of implying it will finish.
- ADMIN-B47 **Uploaded wallpapers** (ADR 0037). Under the built-in swatches, "Your images" lists the images administrators uploaded, each a swatch of its own thumbnail with its name (the file name without its folder, extension or control characters, at most 80 characters; a label only, never part of a path) and a delete button, followed by an "Upload image" tile. `POST /admin/wallpapers` (multipart, one field `file`; admin only) checks, in order: the declared length against `WALLPAPER_MAX_MB` (default 10) plus the multipart framing, so an oversized body is never read, and the file's own size; that no more than 20 images are kept (`limit_reached`); the first bytes (JPEG, PNG or WebP, never the name or declared type: `unsupported_type`); then, decoding with sharp in process, a header claiming more than 48 million pixels (`too_many_pixels`, before any decoding), more than one frame (`animated`), a long edge under 1280 pixels (`too_small`) or an image that does not decode (`unreadable`). Each refusal is 422 `rule_violation` with that reason, said in words under the tile, and stores nothing. An accepted image has its EXIF orientation applied, is fitted inside 3840 × 2160 without enlarging, and is re-encoded as WebP (quality 80); a 480-pixel-wide WebP thumbnail is made from it. Only these two are stored, under random names as `files` rows under `FILES_DIR` (so backups carry them), never the uploaded bytes: no metadata (EXIF, GPS, comments, profiles) survives. The tone (light at an average brightness of 0.5 or above) and the accent (ADR 0037) are measured on the server from the decoded pixels; values a browser sends are refused. `GET /admin/wallpapers` lists them (admin only). Choosing one saves its id as `workspace.wallpaper` (an id that names no uploaded image is refused, 422) and repaints the page at once. Every signed-in member's pages are drawn on it: `GET /wallpapers/:id` and `GET /wallpapers/:id/thumbnail` serve the image with `Content-Type: image/webp`, `Content-Disposition: inline`, `X-Content-Type-Options: nosniff` and `Cache-Control: private, max-age=31536000, immutable`, since an id's image never changes, and 401 without a session; a page carries the address in `--wallpaper-image` and the image's accent in custom properties. Built-in wallpapers cannot be deleted. Delete asks first and is for good: `DELETE /admin/wallpapers/:id` removes the rows and both binaries, and when the image is the chosen wallpaper the setting returns to the default, Jade, in the same transaction, which the confirmation says beforehand. Upload and delete are written to the audit log (Created and Deleted wallpaper, with its name), and choosing an uploaded image reads there as "Your image". When the images cannot be loaded the picker says so in words, offers no upload, and keeps the built-ins usable.

## Deployment configuration

- ADMIN-B17 Startup refuses a production configuration whose `APP_URL` is not HTTPS, unless the URL points at a loopback host (the documented opt-out for smoke-testing a production image locally). The session cookie's `Secure` flag is derived from that validated deployment mode rather than from the raw URL string, so a deployment typo cannot silently emit a non-Secure bearer cookie.
- ADMIN-B20 The client address is resolved from `X-Forwarded-For` by walking the chain right to left and taking the first hop outside `TRUSTED_PROXY_CIDRS`; a prepended address is therefore inert. With no proxy configured, an absent header, or an all-proxy chain, the address is unknown and no per-address control applies rather than every request sharing one placeholder. Login throttling counts the email and the client address as independent buckets, five failures each per 15 minutes: neither their union nor an unknown address can lock an account or an installation that neither key reached (ADR 0013).
- ADMIN-B21 Every login path performs exactly one argon2 verification. Unknown, deleted and deactivated accounts verify a process-lifetime placeholder hash generated with identical parameters, so response time cannot distinguish a registered address from an unregistered one.
- ADMIN-B22 `/recovery` is throttled on the client address alone and records its attempts without an email, because the secret being guessed is the installation-wide `RECOVERY_TOKEN` and an email bucket would let recovery traffic lock a named administrator out of login. A configured `RECOVERY_TOKEN` must be at least 32 characters and `TRUSTED_PROXY_CIDRS` must parse, both refused at startup with an actionable message.
- ADMIN-B34 **Security headers.** `src/proxy.ts` applies one policy from `core/http/security-headers.ts` to every response except build assets. HTML documents get a Content Security Policy with a fresh per-request nonce: scripts only from the app's origin or carrying the nonce (`'strict-dynamic'`), no plugins, no `<base>`, forms posting only to the app, and `frame-ancestors 'none'`. Every response is `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`, a Permissions-Policy that denies camera, microphone, geolocation, payment and USB, and `Cross-Origin-Opener-Policy: same-origin`. API responses, downloads included, are `Cache-Control: no-store` with `default-src 'none'`. A production deployment on HTTPS also sends HSTS (one year, subdomains) and `upgrade-insecure-requests`. The CSP exceptions (inline styles, development-only eval) are listed with their reasons in ADR 0025.
- ADMIN-B35 **The database is a local file.** `DATABASE_URL` is a `file:` URL naming the SQLite database (`file:/var/lib/enan/data/enan.db` in the image); startup refuses any other scheme and a path it cannot create or open, naming the fix. The application, the migrator, the schema audit and the backup commands all open that one path, so there is no second server for any of them to reach. The file and its `-wal` and `-shm` siblings must be on local disk, never a network or synced file system. There is no database network traffic and therefore no database TLS policy. See ADR 0029.
- ADMIN-B50 **A database from before the rename is kept.** The product was called ExecutiveOS, and its image kept the database at `executiveos.db`. When the configured file is named `enan.db` and does not exist, and `executiveos.db` exists in the same directory, the first open renames it, with its `-wal` and `-shm` files, to the new name before anything reads it. An existing `enan.db` is never replaced. See ADR 0048.
- ADMIN-B51 **An install's own Arabic faces.** `FONTS_DIR` (default `/var/lib/enan/fonts`) may hold woff2 files named `text-<weight>.woff2` and `display-<weight>.woff2`; when it does, they become the Arabic text and display faces, served by `GET /api/v1/fonts/<file>` with a generated `faces.css`. They cover the Arabic block only, so Latin stays in Inter, and a weight they lack is drawn in their nearest weight, and only Arabic characters they do not contain fall through to Noto Sans Arabic. Any other file name is not served. With no such files nothing changes. The repository ships no such fonts; an operator adds files they are licensed to serve. See ADR 0049.
- ADMIN-B52 **Installs as one web app.** `/manifest.webmanifest` (`src/app/manifest.ts`, linked from every page) names `id`, `start_url` and `scope` as `/` with `display: standalone`, so a phone's home-screen app owns every page of the origin wherever it was added from. The home-screen icon is the mark's tile (`docs/enan-mark.svg`, the mint mark on dark green) as opaque PNGs: 192 and 512 px in the manifest and a 180 px `apple-touch-icon` (`public/apple-icon.png`), because iOS ignores SVG icons and fills transparency with black. Every in-app link is same-origin, relative and opens in the same window; only external links in rendered markdown open a new one.
- ADMIN-B53 **The installed app fills the screen.** Every page declares `viewport-fit=cover` and a `black-translucent` status bar, so a home-screen app draws under the status bar and the home indicator instead of beside a black band, and iOS reports the real safe-area insets. The shell header pads itself below the status bar, the floating bottom bar sits inside the home indicator's area, 8 px less than its inset from the edge (never under 12 px), as an iOS tab bar does, and the sign-in pages keep their controls inside the safe area.
- ADMIN-B54 **Releases and channels.** `GET /api/v1/health` reports `version` (from `package.json`) and `revision` (the commit the image was built from, `ENAN_REVISION`). Every commit of main publishes `ghcr.io/tsubaie/enan:<sha>`, labelled with its version, revision, `org.enan.schema` and `org.enan.contract`. `:edge` moves to a commit only after its gate passed; a tag `vX.Y.Z` on a checked commit of main whose `package.json` says `X.Y.Z` publishes `:X.Y.Z`, `:X.Y`, `:X` and `:latest` from that same image and creates the GitHub Release (a pre-release gets its own tag only). An image that failed any check never becomes a channel tag. See ADR 0050.
- ADMIN-B55 **Migrations the previous release can run on.** After migration 0006, a migration with a destructive statement (`DROP TABLE`, `DROP COLUMN`, `RENAME`, `DROP INDEX`, `DROP VIEW`, `DROP TRIGGER`) fails `audit:migrations` unless it declares `-- enan:contract` (the previous release cannot run on it) or `-- enan:compatible <reason>`. The image's `org.enan.schema` is how many migrations it applies and `org.enan.contract` the position of its newest contract migration (0 for none); going back from image C to image R is safe exactly when C's contract is at most R's schema. CI starts each image on a fresh database, then starts the current `:edge` on the database it migrated and requires both to be healthy, unless the labels rule that rollback out. See ADR 0050.
- ADMIN-B56 **Automatic updates.** With `docker compose --profile autoupdate up -d`, the `updater` service checks the app's channel every `ENAN_UPDATE_INTERVAL` (default 15m; optionally only inside `ENAN_UPDATE_WINDOW`, in `ENAN_UPDATE_TZ`). For a new digest it pulls the image and holds back a new major version (`ENAN_ALLOW_MAJOR`) or one whose `org.enan.contract` exceeds the running image's `org.enan.schema` (`ENAN_ALLOW_CONTRACT`). Otherwise it backs up with `pnpm backup:create` and, only if that succeeds, replaces the app container with one on the new image that keeps every setting compose gave it. It then requires the container to be healthy and `/api/v1/health` to report the new image's version and revision within `ENAN_HEALTH_TIMEOUT`. On failure it puts the previous container back and never restores the database; the status names the backup and the restore command, and the failed image is not tried again until `retry`. An update interrupted by a restart is finished if the new container verifies, and reversed otherwise. `status.json` and `history.jsonl` (the last 50 outcomes) are on the `updater-status` volume; `check`, `pause`, `resume`, `retry` and `rollback` are queued on `updater-commands` by `docker compose exec updater enan-updater <command>`. Every outcome except a quiet check is POSTed to `ENAN_ALERT_WEBHOOK`, a newer updater image is reported once, and the container turns unhealthy when checks stop. See ADR 0051.
- ADMIN-B18 Log redaction is recursive: passwords, tokens, cookies, authorization headers, API keys, prompt bodies and private notes are censored at every nesting depth, in arrays as well as objects, and errors are serialized through an allowlist of type, message, stack and cause so a thrown `AppError`'s details never reach a durable log. The one-time `SETUP_TOKEN` line (ADMIN-B01) is deliberately printed in full; reading it requires privileged access to the container log.

- ADMIN-B27 **Model eligibility and filtering**: Catalog discovery uses authenticated `/v1/models/user`, paginated without following arbitrary response URLs, so account provider/privacy restrictions apply before local filtering. Offer namespaced text models with structured outputs, positive output capacity and enough context for each model slot; omit batch-only variants. Cache catalog metadata for sixty seconds per credential fingerprint. Before displaying or admitting a model, consult the latest invocation in the past hour (after saved-key replacement); a latest 404/model-routing failure temporarily excludes that model until the window expires or a later invocation succeeds. Do not change saved selections silently: show an unavailable selection and require a replacement before saving. Both selectors support case-insensitive multi-word search across model name/ID/provider, a provider filter, result count, empty state and clear action; filtering preserves the current eligible selection. Catalog eligibility is not a guarantee of future routing or input-specific context fit. Tests/audits remain pending.

ADMIN-B27 model/provider menus use the shared searchable ChoiceSelect controls. Model discovery and connection queries do not poll or refetch on window focus while editing the AI form; explicit refresh and mutation invalidation update them. This keeps open menus and in-progress selections stable.

ADMIN-B26 admission failures distinguish hourly limits (including failed jobs, with estimated retry delay from the oldest request in the rolling window), workspace budget exhaustion and input context limits. ADMIN-B26 hourly AI admission limits are controlled by `AI_RATE_LIMIT_ENABLED` (default `true`). Setting it to `false` disables the app's per-user hourly refinement/breakdown/tag request cap for development, without deleting attempt history or changing workspace token-budget, concurrency or provider limits. Configuration is read on startup. The maintainer requested this local development override; see ADR 0018.
