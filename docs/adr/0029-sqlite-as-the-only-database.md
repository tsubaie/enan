# ADR 0029 — SQLite as the only database

**Status:** accepted (2026-10-16). Supersedes ADR 0002 and ADR 0027 entirely, the backup mechanism of ADR 0008 (the "no CLI" rule itself stands and becomes stricter) and the database TLS part of ADR 0025 (the security headers stand).

## Context

ADR 0002 chose PostgreSQL 16 because multi-user writes, `SKIP LOCKED` job claims and array columns seemed to need it. Two things have changed since. ADR 0003 fixed the deployment at exactly one application process, so the job runner never competes with another instance for claims, and the data volume of one executive office is small: a few people writing, lists of hundreds of rows, searches over a few thousand. What PostgreSQL costs that office is a second service to run, back up, secure and upgrade: a `db` container with its own volume and password, a TLS policy for remote hosts (ADR 0025, ADR 0027), `pg_dump` and `pg_restore` in the image, a pool, an advisory-lock vocabulary, and a separate test server for every developer and CI job.

The maintainer decided that self-hosting simplicity wins: one container, one data volume, one file. Work item WI-0003 carried the migration out; this record fixes the decisions it was built on.

## Decision

**SQLite is the only database.** The application opens one database file through `@libsql/client` with a `file:` URL, used through `drizzle-orm/libsql`. The client is asynchronous, so every `await db.transaction(async tx => …)` and nested savepoint in the codebase keeps its shape, and it keeps a small connection pool so each open transaction holds its own connection.

- **Every transaction is immediate.** `BEGIN IMMEDIATE` takes the write lock at the start, so contention happens only there. A deferred transaction that reads and then writes would fail with `SQLITE_BUSY_SNAPSHOT`, which cannot be retried in place.
- **Writers of one process queue in JavaScript.** `src/core/db/client.ts` keeps one process-wide write queue (on `globalThis`, because the production bundle carries a copy of the module per server chunk): a transaction opened on the pool waits its turn, bounded by a window on the order of ten seconds, and then runs `BEGIN IMMEDIATE` with the lock free. A `BEGIN IMMEDIATE` the driver refuses with `SQLITE_BUSY` must never be retried: it leaves its statement pending on that pooled connection and every later `COMMIT` on it fails with "SQL statements in progress". A transaction requested on the pool from inside a running one would wait on its own lock, so it is refused at once as a programming error; services take the request's handle, where the call is a savepoint. Only another process (the restore command, a script) can still make `BEGIN` wait; the driver's `busy_timeout` (two seconds, a blocking wait that is safe because no in-process holder reaches it) covers that, after which the pool is reopened to drop the poisoned connection and the caller gets `DatabaseBusyError`.
- **Pragmas.** `journal_mode = WAL`, `synchronous = NORMAL` and `foreign_keys = ON` are applied when the client is created and after every reopen, on every pooled connection; `busy_timeout` is the driver's two-second wait above. WAL lets readers proceed during a write; foreign keys are off by default in SQLite and must be switched on per connection.
- **Location.** `DATABASE_URL` keeps its name and takes a `file:` URL: `file:/var/lib/executiveos/data/executiveos.db` in production, on the `data` volume, and `file:./tmp/dev.db` in development. Any other scheme is refused at startup. The file and its `-wal` and `-shm` siblings must live on a local disk, never on NFS, SMB or a synced folder, because SQLite's locking depends on it. `DATABASE_SSL_ROOT_CERT`, `DB_POOL_MAX` and `POSTGRES_PASSWORD` no longer exist.
- **Test databases.** The `_test` rule applies to the file name: the path's basename must end in `_test.db`, and every Vitest worker gets its own file.
- **Migrations.** One SQLite migration, `drizzle/0000_initial.sql`, generated from the converted schema plus hand-written statements for the trigger and the partial indexes. The seventeen PostgreSQL migrations and their `meta` folder are gone; there is no data migration from a PostgreSQL instance (the only deployment was a development preview, re-seeded). The runner applies migrations inside one immediate transaction; with one application process (ADR 0003) that is the migration lock.
- **No SQL functions.** SQLite generated columns cannot call application code, and registering a JavaScript function on every pooled connection is fragile. `search_text` is a plain `text` column the repo writes on every insert and update using `normalize()` from `src/core/search/normalize.ts`, which ports `eos_normalize` exactly. The corpus is `normalize(name) + '\n' + normalize(rest…)`, so a prefix match on the corpus is a prefix match on the name and the rank is `case when search_text like <prefix> then 0 else 1 end`. Trigram indexes are dropped; `LIKE '%q%'` scans are acceptable at this scale.
- **Types.** `uuid` columns are `text` (ids are still UUID v7 from `ids.ts`); timestamps are `integer` milliseconds since the epoch (`mode: 'timestamp_ms'`, so Drizzle still returns `Date` and the API still emits ISO strings); `jsonb` and arrays are JSON text (`mode: 'json'`), and array facets use `json_each`. `ON CONFLICT … DO UPDATE` and `RETURNING` are supported and kept.
- **The task depth invariant (TASKS-I01) stays in the database** as a trigger: `BEFORE INSERT` and `BEFORE UPDATE OF parent_id` raising `TASKS-I01 depth one required` under the same three predicates, registered in `drizzle/custom-objects.json`; the repo maps the raised message to the error the PostgreSQL check produced.
- **The task order constraint becomes a partial unique index**, `tasks_active_order_idx on tasks(coalesce(parent_id, ''), sort_order) where deleted_at is null`. SQLite cannot defer it, so a reorder that would collide inside a transaction first moves the affected rows to temporary negative `sort_order` values and then to their final values.
- **Locks are in-process.** `pg_advisory_xact_lock` calls are deleted: an immediate transaction already serializes writers. The restore lock (`withSessionLock`) is an in-process asynchronous lock keyed by number in `src/core/db/locks.ts`, with the same return shape.
- **Backups are a file snapshot.** `createBackup` writes `db.sqlite` with `VACUUM INTO` into the staging directory (a consistent online snapshot), then the files tar and the manifest as before. `restoreBackup` keeps the staged-files flow (ADR 0024, ADR 0026) and replaces `pg_restore` with: close the client, verify the backup file with `PRAGMA integrity_check` on a separate connection, swap the live file (write beside it, `rename` over it, delete `-wal` and `-shm`), reopen the client. Maintenance mode, the serialized restore lock and ADMIN-B31 to B33 keep their meaning.
- **No subprocesses at all.** ADR 0008 allowed `child_process` only in `core/backup` for the bundled PostgreSQL binaries. Nothing needs it now; the audit forbids `child_process` everywhere.
- **Schema audit.** `audit:schema` keeps its job. `introspect.ts` reads `sqlite_master` and the `pragma_table_info`, `pragma_index_list` and `pragma_foreign_key_list` table functions instead of `information_schema` and `pg_catalog`. `custom-objects.json` lists `triggers` and `indexes` only.

## Consequences

- Self-hosting is one container with a `data` volume. Compose has no `db` service, no database password and no published database port; the image is `node:22-bookworm-slim` with no PostgreSQL client. The backup is the file plus the files tar, restorable by copying.
- Tests need no server: `DATABASE_URL_TEST` is a `file:` path under `tmp/`, CI drops its service containers, and `docker-compose.test.yml` is gone.
- Writes are serialized. Two requests that both write wait on each other in the write queue, up to its window, after which the later one fails with a retryable database error. For one office this is invisible; it is also why multi-instance mode stays out of scope.
- Search is a `LIKE` scan over normalized text rather than a trigram index. It is fast enough for the data this product holds; FTS5 is the upgrade path if that changes.
- A repo that forgets to write `search_text` ships a record search cannot find. The repo tests and the search tests cover every searchable table.
- The database file must be on local disk. A deployment that mounts the `data` volume from a network share will see lock errors or corruption, and the documentation says so.
- The restore swaps a file while the client is closed; a request arriving during that window gets the maintenance 503, as before.
- Accepted ADRs are not edited: 0002, 0008, 0025 and 0027 gain a superseded-by line and nothing else. Their text still describes what the PostgreSQL version did.

## Alternatives considered

- **Keep PostgreSQL.** Works, but every cost in Context stays for an office that gains nothing from it. Rejected by the maintainer.
- **`better-sqlite3` (synchronous).** Simpler driver, but every transaction in the codebase awaits inside it, and a synchronous driver would need every repo and service rewritten or a worker thread to host the database. Rejected.
- **Deferred transactions with `busy_timeout`.** A read-then-write transaction upgrades its lock mid-way and fails with `SQLITE_BUSY_SNAPSHOT`, which no timeout cures, and a native wait for an in-process holder blocks the event loop that holder needs. Rejected.
- **Retrying a refused `BEGIN IMMEDIATE`.** The first design; it poisons the pooled connection as described above, which surfaced as every commit failing once two requests had contended. Rejected.
- **Registering `eos_normalize` as a SQLite function to keep generated columns.** Has to be repeated on every pooled connection and is invisible to `drizzle-kit`, `sqlite3` and any other tool that opens the file. Rejected.
- **FTS5 for search.** More machinery than the corpus needs today; left as the upgrade path.
- **Enforcing task order uniqueness in the service only.** Loses the database check that the constraints tests rely on. Kept as the fallback if the two-step reorder proves impractical; the hand-off must say so.
- **Backing up with the online backup API or copying the file.** `VACUUM INTO` gives a consistent, compacted snapshot with one statement and no extra binding. Copying a live WAL database is not consistent.
